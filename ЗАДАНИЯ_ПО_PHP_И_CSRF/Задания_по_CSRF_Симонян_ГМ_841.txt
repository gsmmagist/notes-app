Задание 1: Анализ уязвимостей к CSRF-атакам

1. Уязвимость каждого маршрута к CSRF

GET /ads: Не уязвим. Это маршрут только для чтения данных (идемпотентный), CSRF-атаки нацелены на state-changing операции. Браузер не выполняет автоматические GET-запросы без взаимодействия пользователя в контексте, изменяющем состояние.

POST /ads/create: Уязвим. Требует авторизации, но без защиты (токена) злоумышленник может подделать POST-запрос от имени авторизованного пользователя, создав объявление с вредоносными данными.

POST /ads/delete: Уязвим. Аналогично, позволяет удалить объявление без проверки источника запроса, используя куки авторизации жертвы.

POST /profile/update: Уязвим. Изменяет профиль (например, email, пароль), что критично для аккаунта; без токена возможна подмена данных.

2. Сценарии атак для двух наиболее опасных маршрутов (POST /ads/delete и POST /profile/update)

Атака на POST /ads/delete:
Злоумышленник создаёт вредоносную страницу (например, на своём сайте или в email) с формой: <form action="https://app.example.com/ads/delete" method="POST"><input type="hidden" name="ad_id" value="123"><input type="submit" value="Кликни для выигрыша!"></form> (или авто-отправка через JS form.submit()).
Жертва (авторизованная в приложении) посещает страницу и кликает (или форма отправляется автоматически).
Браузер отправляет POST с куки-сессией жертвы; сервер удаляет объявление ID=123, так как проверяет только авторизацию. Данные пользователя: потеря объявления без его ведома.

Атака на POST /profile/update:
Злоумышленник размещает форму: <form action="https://app.example.com/profile/update" method="POST"><input type="hidden" name="email" value="hacker@example.com"><input type="submit" value="Обновить профиль"></form>.
Жертва кликает ссылку/кнопку на фишинговом сайте.
Сервер обновляет email жертвы на контролируемый злоумышленником, позволяя захват аккаунта (сброс пароля). Данные: компрометация профиля, потеря контроля над аккаунтом.

Эта схема типична для CSRF: использует существующие куки без дополнительных проверок.

3. Отчёт об уязвимостях

Маршрут: GET /ads
Уровень риска: Низкий
Обоснование: Идемпотентный GET, не меняет состояние; CSRF не применим.

Маршрут: POST /ads/create
Уровень риска: Высокий
Обоснование: Создаёт данные (спам/вредоносное объявление); массовый эффект при фишинге.

Маршрут: POST /ads/delete
Уровень риска: Высокий
Обоснование: Удаление данных безвозвратно; прямой ущерб пользователю.

Маршрут: POST /profile/update
Уровень риска: Высокий
Обоснование: Изменение профиля ведёт к компрометации аккаунта; критично для безопасности.


Задание 2: Архитектура CSRF-защиты

1. Общая архитектура и хранение токена

Токен генерируется сервером (криптостойкий, e.g. bin2hex(random_bytes(32))) при рендере формы или начале сессии. Хранится в сессии PHP ($_SESSION['csrf_token']), а не в БД:
- Сессия привязана к пользователю и IP/браузеру, предотвращая replay-атаки.
- БД требует доп. запросов (нагрузка), не масштабируема для одноразовых токенов; сессия — в памяти/файлах, быстрее и безопаснее для временных данных.
- Токен передаётся клиенту как hidden field в форме или header (X-CSRF-Token для AJAX).

2. Схема жизненного цикла токена (ASCII):
1. Генерация: При рендере формы (Controller/View) -> random_token -> $_SESSION['csrf_token'] = token
   ↓
2. Передача: Вставка в HTML: <input type="hidden" name="csrf_token" value="{token}">
   ↓
3. Хранение в форме: Клиент (браузер) держит в DOM
   ↓
4. Отправка: POST-запрос с token в body/header
   ↓
5. Проверка: Controller -> if (!hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) -> reject
   ↓
6. Несовпадение: 403 Forbidden, unset token, лог; не раскрывать детали ошибки (без "CSRF failed").

Токен одноразовый/с таймаутом (e.g. 30 мин), ротируется после валидации.

4. Псевдокод базового класса CsrfGuard

class CsrfGuard {
    private $sessionKey = 'csrf_token';

    public function generate() {
        if (empty($_SESSION[$this->sessionKey])) {
            $_SESSION[$this->sessionKey] = bin2hex(random_bytes(32));  // Криптостойкий токен
        }
        return $_SESSION[$this->sessionKey];
    }

    public function validate($inputToken) {
        if (empty($_SESSION[$this->sessionKey]) || empty($inputToken)) {
            return false;
        }
        $valid = hash_equals($_SESSION[$this->sessionKey], $inputToken);  // Timing-safe сравнение
        if ($valid) {
            unset($_SESSION[$this->sessionKey]);  // Одноразовый
        }
        return $valid;
    }

    public function embed() {
        echo '<input type="hidden" name="csrf_token" value="' . htmlspecialchars($this->generate()) . '">';
    }
}

Использование: В контроллере перед формой $guard = new CsrfGuard(); $guard->embed(); при POST: if (!$guard->validate($_POST['csrf_token'])) { /* reject */ }

5. HTTP-ответы сервера

Успешная проверка: 200 OK (или 2xx для редиректа/JSON). Продолжает обработку; стандарт для нормальных запросов.

Неуспешная: 403 Forbidden - указывает "доступ запрещён" без деталей (не помогает атакующему).
